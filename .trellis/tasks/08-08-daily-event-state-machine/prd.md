# 日常战斗事件状态机审计与统一恢复

## Goal

把日常挂机（经验本 / 纽本 + 战斗中事件）的执行从“发现一个界面补一个模板”的临时补丁模式，改为一次状态机级审计后统一恢复：为每个可复现页面定义明确的识别条件、动作、成功后的下一状态、以及超时/失败出口，确保任何未知或残留页面都不会被错误当成“继续寻找纽本入口”，并用可自动运行的回归测试固化这些出口。

## Background

fork 为“连续场次不回主页换饼”做了优化：删掉了原作者每场后的 `back_init_menu()`，改为 `_run_daily_group` 一组跑完才回一次主页。副作用是：纽本战斗中的事件结果页（如判定成功后约 40 秒动画才出现的“继续”）没有被及时清掉，就被下一场 `thread_luxcavation()` 的入口寻找撞上，30 轮后报“无法进入纽本”，且 `back_init_menu()` 也离不开该事件页。

根因两处叠加：
1. `Battle.fight()` 的事件路径只做模板点击（continue/proceed/commence/perform_check…），beta 截图上这些模板相似度不足阈值时不点击，且没有 OCR 兜底；事件结果页迟迟出现时 `fight()` 可能已因超时/chance 逻辑退出。
2. 连续场次导航（`onetime_thread_process` / `_run_daily_group`）在进入下一场入口前，未对“非采光菜单页/残留事件页”做恢复。

对照原作者 KIYI671 仓库确认：`fight()` 事件处理逻辑 fork 与原版一致；差异只在 fork 删除了每场的 `back_init_menu()`。

## Requirements

### R1 状态机审计

梳理日常执行涉及的全部页面/状态，产出一张状态表，每个状态至少记录：识别条件（模板/OCR）、动作、成功后下一状态、超时与失败出口。覆盖范围至少：

- 采光入口（经验本 / 纽本）、编队、开始战斗；
- 服务器错误：游戏自身倒计时（重试N）、可用金色重试、长期不可用（关闭并重启）；
- 日常事件：选项页（第一个选项禁用需改选）、罪人判定（献上土偶不可用→改献上罪人）、判定结果页“判定成功/失败→继续”；
- 战斗胜利确认结算页；
- 副本入口失败、战斗失败、回主页恢复。

涉及代码：`tasks/battle/battle.py::Battle.fight()`（约 216–579）、`tasks/event/event_handling.py`、`tasks/daily/luxcavation.py`、`tasks/base/script_task_scheme.py`、`tasks/base/back_init_menu.py`。

### R2 事件出口识别（OCR 兜底 + 耐心）

`fight()` 的事件路径在模板匹配失败时必须有 OCR 兜底：当页面 OCR 命中“判定成功/判定失败/继续/进行判定”等关键字时，点击对应“继续/进行判定”按钮推进，而不是提前退出。对事件结果页要保持耐心（结果按钮可能需数十秒动画后才出现），不得因 chance 耗尽在事件页误判为失败并离开。识别必须基于实际 beta 截图重建，不能仅凭 1.5.1 日志假设旧模板仍适用。

### R3 连续场次导航恢复

连续场次导航在进入下一场入口之前，必须对“非采光菜单页 / 残留事件页”做统一恢复（把界面拉回可进入采光的已知状态），再执行 `thread_luxcavation()` 的入口寻找。恢复逻辑要覆盖当前 `back_init_menu()` 尚不能离开的日常事件页，避免残留页被当作“继续找入口”。同时保留既有的“同项目连续场次不回主页、项目结束回主页换饼一次”优化，不得退回到每场都回主页。

### R4 回归测试

为上述状态出口建立可自动运行的回归表/测试（pytest）。先让新增测试红灯，再统一实现转绿。测试至少覆盖 R1 列出的各状态识别与出口，尤其是“事件结果页→继续”“残留事件页→恢复→重新进入采光”两条此前失败的路径。

## Non-Goals

- 不重写整个 `fight()` 战斗循环，只在既有事件路径上增加 OCR 兜底与耐心；不改动镜牢/普通战斗主逻辑。
- 不为“献上土偶/罪人”等单一事件写专用硬编码补丁（通用 OCR 推进除外）。
- 不改变既有连续场次优化（同项目连战不回主页、项目结束回主页换饼一次）。
- 不新增第三方依赖，不重构 OCR/模板匹配底层。
- 不做模拟器/英文多语言适配扩展，仅保证现有中文路径。
